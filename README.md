# CADI Agentic Search

**AI-powered search for the CADI website at the University of Portsmouth**

A self-contained, single-file search interface that uses Claude (Anthropic's AI) to interpret natural language queries from staff and return the most relevant pages from the CADI website. The search index is automatically refreshed weekly by a GitHub Actions crawler.

## 1. How it works

The system has four moving parts that work together:

```
Staff member types a query
        ↓
index.html (browser)
  — fetches search-index.json from GitHub (live page data)
  — scores the index locally against the query
  — sends query + top 20 most relevant pages to Cloudflare Worker
        ↓
Cloudflare Worker (API proxy)
  — holds the Anthropic API key securely
  — forwards the request to Claude
        ↓
Claude (claude-sonnet-4-20250514)
  — reads the query and the focused page index
  — returns ranked results with relevance scores and reasoning
  — if no relevant pages were found, says so clearly
        ↓
index.html renders results to the user
```

Separately, a GitHub Actions workflow runs every Sunday at 2am UTC. It executes `scripts/crawl.py` against `https://cadi.port.ac.uk`, produces a fresh `search-index.json`, and commits it back to the repository. The next time a user searches, their browser fetches this updated index automatically.

**No backend server is required.** The only server-side component is the lightweight Cloudflare Worker, which exists solely to keep the Anthropic API key out of the browser.

## 3. The search interface (index.html)

The entire frontend is a single HTML file. It uses React (loaded from a CDN) with Babel for JSX transpilation in-browser, meaning no build step, no Node.js, and no npm are needed. You can open the file directly in a browser for development.

### Key sections inside index.html

**`CONFIGURATION`** (top of the `<script>` block) — the two values you must set before deploying:

```js
const PROXY_URL = "https://cadi-search-proxy.kristian-band.workers.dev";
const GITHUB_RAW_INDEX_URL = "https://raw.githubusercontent.com/.../search-index.json";
```

**`PRIORITY_PAGES`** — an array of pages that receive a relevance boost for specific search terms. Add pages here if they should consistently rank highly for certain queries (e.g. the CPD page for any CPD-related search).

```js
const PRIORITY_PAGES = [
  {
    url: "https://cadi.port.ac.uk/cpd-support",
    boost_terms: ["cpd", "professional development", "workshops"],
  },
  ...
];
```

> **Note:** Priority pages are passed to Claude in the system prompt as a nudge, not a hard override. Claude may not always honour them depending on the query.

**`EXTERNAL_LINKS`** — a list of external tools (e.g. APEX, Moodle, ObserveWell) that are surfaced directly above the AI results when a user's query matches their keywords. These bypass Claude entirely — matching is done locally in the browser using simple string matching.

```js
const EXTERNAL_LINKS = [
  {
    name: "APEX",
    url: "https://apex.port.ac.uk",
    description: "Academic Practice Enhancement Platform",
    keywords: ["apex", "academic practice enhancement"],
  },
  ...
];
```

**`EXAMPLE_PROMPTS`** — the chip buttons shown below the search box. Update these to reflect the most common things staff search for.

**`FALLBACK_INDEX`** — a small hardcoded array of pages used if the live `search-index.json` cannot be fetched (e.g. CORS error, network issue, or the GitHub URL is not yet configured). Keep this reasonably up to date with the most important pages, but it is a safety net, not the primary index.

### How a search works (step by step)

1. The user types a query and presses Enter or clicks the search button.
2. The browser scores the full index locally against the query (see [Relevance scoring](#relevance-scoring) below) and selects the top 20 most relevant pages.
3. The browser POSTs to the Cloudflare Worker URL with a JSON body containing the Claude model, a system prompt, and the user's query alongside only the scored pages.
4. The Worker adds the `x-api-key` header (Anthropic API key) and forwards the request to `api.anthropic.com/v1/messages`.
5. Claude reads the system prompt and the user content (query + scored pages), then returns a JSON object with: `reasoning`, `results` (ranked array of page IDs with scores), `content_gap`, and `suggestions`.
6. The browser matches the result IDs back to full page records from the index, sorts by `relevance_score`, and renders the cards.

### Relevance scoring

Before every API call, two functions filter the index down to the most relevant pages for the query:

**`getCorePages(index)`** — detects the homepage, contact page, and about page by URL pattern (no hardcoded IDs). The homepage is identified by a path of `/` or empty; contact and about are found by `/contact` and `/about` in the URL. These three pages are always included in the index sent to Claude regardless of their relevance score.

**`scorePages(index, query, topN = 20)`** — scores every page against the query across four fields with weighted points:

| Field | Points per matching word |
|---|---|
| Title | 10 |
| Tags | 8 |
| Tag string (multi-word tags) | 5 |
| Excerpt | 4 |
| Content (first 600 chars) | 2 |

Matching uses a fuzzy comparator that handles misspellings and partial words — for example `felowship` matches `fellowship`, and `timetab;e` matches `timetable`. Pages are sorted by descending score and the top 20 are returned. Core pages (homepage, contact, about) are appended if not already in the top 20.

`scorePages` returns `{ pages, maxScore }`. When `maxScore` is 0 — meaning no page scored any points — an additional instruction is injected into the Claude system prompt telling it to acknowledge that no strong match was found and to suggest the user tries a different search term or contacts the team.

### The Claude system prompt

The system prompt is defined inline in the `runSearch` function. It instructs Claude to:

- Understand intent rather than doing literal keyword matching
- Expand common abbreviations (ABL, AIR, APEX, HEA, etc.)
- Return only results with a relevance score of 35 or above
- Honestly flag when a topic has no coverage in the index
- When `maxScore === 0`, say so honestly rather than returning unrelated results
- Respond exclusively in valid JSON with no preamble or markdown fences

To change the AI's behaviour, edit the `systemPrompt` string inside `runSearch`.

## 4. The site crawler (scripts/crawl.py)

The crawler is a straightforward Python script that performs a breadth-first crawl of the CADI website and outputs a structured JSON file.

### Running the crawler manually

```bash
# Install dependencies (Python 3.11+ recommended)
pip install requests beautifulsoup4 lxml

# Run against the live site
python scripts/crawl.py \
  --url https://cadi.port.ac.uk \
  --max-pages 300 \
  --output search-index.json
```

| Argument | Default | Description |
|---|---|---|
| `--url` | *(required)* | Root URL to start crawling from |
| `--max-pages` | `300` | Maximum number of pages to index |
| `--stay-on-domain` | `true` | If `true`, only follows links on the same domain |
| `--output` | `search-index.json` | Output file path |

### How the crawler works

1. Starts at the root URL and maintains a queue of URLs to visit.
2. Reads `robots.txt` and skips any disallowed paths.
3. For each page it fetches, it:
   - Strips navigation chrome, headers, footers, scripts, and CADI-specific noise elements (`NOISE_TAGS`)
   - Extracts the main content using a priority list of CSS selectors (`CONTENT_SELECTORS`) — tuned specifically for Drupal's HTML structure
   - Extracts supplemental content from signposts, quotes, and accordion components (`SUPPLEMENTAL_SELECTORS`)
   - Infers the content type (page, event, resource, guide) from URL patterns and Drupal body classes
   - Extracts meta tags for description, date, and tags
4. Writes a JSON file with a record per page (see [Section 5](#5-the-search-index-search-indexjson)).
5. Waits 0.5 seconds between each request to be polite to the server (`CRAWL_DELAY`).

### Adapting the crawler for a different site

If the CADI Drupal site is ever restructured, the selectors may need updating:

- **`CONTENT_SELECTORS`** — ordered list of CSS selectors tried in sequence to find the main content area. If the Drupal theme changes its class names, update these.
- **`NOISE_TAGS`** — elements to strip before extracting text. Add selectors for any new persistent UI chrome (cookie banners, chat widgets, etc.).
- **`SUPPLEMENTAL_SELECTORS`** — CADI-specific components whose text should be appended to the main content even if they sit outside the primary content container.
- **`infer_content_type`** — the heuristic for deciding whether a page is a `page`, `event`, `resource`, or `guide`. Update the URL patterns and Drupal body classes to match any new content types.

## 5. The search index (search-index.json)

This file is committed to the repository and served as a raw GitHub file. It is fetched by the browser on every page load and scored locally. Only the top 20 scored pages are passed to Claude per search.

```json
{
  "generated_at": "2026-05-10T05:27:02Z",
  "source_url": "https://cadi.port.ac.uk",
  "total_pages": 181,
  "pages": [
    {
      "id": 1,
      "url": "https://cadi.port.ac.uk/cpd-support",
      "title": "CPD and Support | CADI",
      "excerpt": "First 300 characters of extracted text…",
      "content": "First 1500 characters of extracted text (used for scoring and sent to Claude)",
      "type": "page",
      "tags": ["cpd", "workshops"],
      "date": "2026-03-01",
      "description": "Meta description from the page"
    },
    ...
  ],
  "errors": [
    { "url": "https://cadi.port.ac.uk/broken", "status": 404 }
  ]
}
```

**Do not edit this file by hand.** It is overwritten entirely on every crawler run.

### Token usage

Because only the top 20 scored pages are passed to Claude, token usage per request is approximately 3,000–5,000 tokens regardless of how large the index grows. This is a ~90% reduction compared to sending the full index, and keeps requests well within the Cloudflare Worker's limits.

For reference: a 182-page index sent in full produces approximately 42,000 input tokens. With scoring, a typical query produces approximately 3,500 input tokens.

The per-page `content` field is additionally truncated to 400 characters inside `runSearch` before being passed to Claude. The `excerpt` field is used for display only and is never sent to the API.

## 6. GitHub Actions (automated crawling)

The workflow file at `.github/workflows/crawl_site.yml` automates the weekly index refresh.

### Schedule

The crawler runs automatically every **Sunday at 2:00am UTC**. This is defined by the cron expression:

```yaml
schedule:
  - cron: '0 2 * * 0'
```

### Running the crawler manually via GitHub

You can trigger a manual run at any time:

1. Go to the repository on GitHub
2. Click **Actions** in the top navigation
3. Select **Crawl and Index Website** from the left sidebar
4. Click **Run workflow**
5. Fill in the optional inputs (URL, max pages, stay on domain) or leave them at their defaults
6. Click **Run workflow** again to start

The workflow will crawl the site, validate the output (fails with an error if zero pages are indexed), commit the updated `search-index.json` back to the repository, and push the change.

### Required GitHub permissions

The workflow uses `permissions: contents: write` to commit the index file. This is already set in the workflow YAML. No additional configuration is needed for public repositories. For private repositories, ensure the default Actions token has write access (Settings → Actions → General → Workflow permissions → "Read and write permissions").

### What happens after the commit

Because `search-index.json` is fetched directly from GitHub's raw URL at search time, the updated index becomes live for all users the next time they perform a search — no deployment step required.

## 7. The Cloudflare Worker (API proxy)

The Cloudflare Worker is a small JavaScript function deployed separately to Cloudflare's edge network. Its sole purpose is to hold the Anthropic API key and forward requests from the browser to the Anthropic API.

**The Worker code is not in this repository.** It was deployed separately and lives at:

```
https://cadi-search-proxy.kristian-band.workers.dev
```

### Why a proxy is necessary

API keys must never be exposed in client-side JavaScript — they would be visible to anyone who opened DevTools. The Worker sits between the browser and Anthropic's API, adding the `x-api-key` header server-side.

### What the Worker does

```
Browser POST → Worker → adds x-api-key → Anthropic API → response back to browser
```

### Recreating the Worker

If the Worker needs to be redeployed (e.g. the Cloudflare account changes), here is a minimal Worker implementation:

```js
export default {
  async fetch(request, env) {
    if (request.method === "OPTIONS") {
      return new Response(null, {
        headers: {
          "Access-Control-Allow-Origin": "*",
          "Access-Control-Allow-Methods": "POST, OPTIONS",
          "Access-Control-Allow-Headers": "Content-Type",
        },
      });
    }

    const body = await request.text();

    const response = await fetch("https://api.anthropic.com/v1/messages", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "x-api-key": env.ANTHROPIC_API_KEY,
        "anthropic-version": "2023-06-01",
      },
      body,
    });

    const data = await response.text();

    return new Response(data, {
      status: response.status,
      headers: {
        "Content-Type": "application/json",
        "Access-Control-Allow-Origin": "*",
      },
    });
  },
};
```

Store the API key as a **Worker secret** named `ANTHROPIC_API_KEY` (not as a plain environment variable) via the Cloudflare dashboard or Wrangler CLI:

```bash
wrangler secret put ANTHROPIC_API_KEY
```

### API key management

The Anthropic API key is managed through the [Anthropic Console](https://console.anthropic.com). If the key needs to be rotated:

1. Generate a new key in the Anthropic Console
2. Update the Worker secret: `wrangler secret put ANTHROPIC_API_KEY`
3. The old key can then be deleted from the Console
4. No changes to `index.html` are needed

## 9. Deployment guide

### First-time setup

**Step 1: Deploy the Cloudflare Worker**

1. Create a Cloudflare account (or use an existing one)
2. Install Wrangler: `npm install -g wrangler`
3. Log in: `wrangler login`
4. Create a new Worker project and paste the Worker code from [Section 7](#7-the-cloudflare-worker-api-proxy)
5. Add the API key as a secret: `wrangler secret put ANTHROPIC_API_KEY`
6. Deploy: `wrangler deploy`
7. Note the Worker URL (e.g. `https://cadi-search-proxy.your-name.workers.dev`)

**Step 2: Configure index.html**

Open `index.html` and update the two constants at the top of the script:

```js
const PROXY_URL = "https://cadi-search-proxy.your-name.workers.dev";
const GITHUB_RAW_INDEX_URL = "https://raw.githubusercontent.com/YOUR-ORG/YOUR-REPO/main/search-index.json";
```

**Step 3: Run the initial crawl**

Either run the crawler locally:

```bash
python scripts/crawl.py --url https://cadi.port.ac.uk --output search-index.json
```

Or trigger the GitHub Actions workflow manually (see [Section 6](#6-github-actions-automated-crawling)).

**Step 4: Commit and push**

Commit `index.html` and `search-index.json` to the repository and push.

**Step 5: Deploy the HTML file**

Deploy `index.html` to wherever it will be served. Options include:

- **GitHub Pages** — enable Pages in the repository settings, set the source to the `main` branch and root directory. The file will be available at `https://your-org.github.io/your-repo/`.
- **Netlify / Vercel** — drag and drop the file or connect the repository. Both support single-file deployments.
- **Drupal** — embed or link from the CADI Drupal site (e.g. as an iFrame, or by hosting the file separately and linking to it).
- **Any static host** — the file is self-contained and has no server-side dependencies.

### Updating after initial deployment

The search index updates automatically every Sunday. To update the UI or configuration:

1. Edit `index.html`
2. Commit and push
3. The change is live immediately (no build step needed)

## 10. Branding and design

The interface follows the University of Portsmouth brand guidelines (September 2024 edition).

### Colour palette

All colours are defined as CSS custom properties on `:root` in the `<style>` block, and as a JavaScript constants object (`C`) in the script. Both must be updated if colours change.

| Token | Name | Hex |
|---|---|---|
| `--primary-dark` | Dark Purple | `#3C023C` |
| `--primary` | Light Purple | `#621360` |
| `--secondary-dark` | Dark Blue | `#0078B4` |
| `--secondary` | Light Blue | `#00A0FF` |
| `--black` | Black | `#000000` |
| `--dark-grey` | Dark Grey | `#505457` |
| `--mid-grey` | Mid Grey | `#ABAAAA` |
| `--light-grey` | Light Grey | `#D1D1D1` |
| `--lighter-grey` | Lighter Grey | `#F7F7F7` |
| `--off-white` | Off White | `#FAFAFA` |
| `--white` | White | `#FFFFFF` |

The page background is a gradient from Dark Purple → Light Purple → Dark Purple. Light Blue (`#00A0FF`) is used as the primary interactive and accent colour (search button, focus states, AI reasoning box, hover glows). Dark Blue (`#0078B4`) is used as the button gradient endpoint.

### Typography

Per the University of Portsmouth brand guidelines, two Google Fonts are used:

- **Encode Sans Expanded** — headings, the CADI logomark, card titles, and numerical labels. Bold (700) and Extra Bold (800) weights.
- **Open Sans** — all body copy, labels, chip buttons, and metadata.

The primary brand font (Aero) is a licensed typeface not available on Google Fonts and is not used in this web interface.

### Result type badges

Each page in the index has a `type` field (`page`, `event`, `resource`, `guide`). These are mapped to badge colours in the `TYPE_CONFIG` object using semi-transparent purple and blue tones from the brand palette:

| Type | Background | Border | Text |
|---|---|---|---|
| page | Purple tint | Purple | Light pink |
| event | Blue tint | Blue | Light blue |
| resource | Light blue tint | Light blue | Pale blue |
| guide | Dark purple tint | Dark purple | Light lavender |

## 11. Maintaining and extending the project

### Adding a new external tool link

Edit the `EXTERNAL_LINKS` array in `index.html`:

```js
{
  name: "Tool Name",
  url: "https://tool.port.ac.uk",
  description: "One-line description of what it does",
  keywords: ["keyword1", "keyword2"],
},
```

Keywords are matched against the user's query using simple case-insensitive `includes()`. The tool card appears above the AI results when any keyword matches.

### Adding a new priority page

Edit the `PRIORITY_PAGES` array:

```js
{
  url: "https://cadi.port.ac.uk/new-page",
  boost_terms: ["term1", "term2"],
},
```

### Updating the example prompts

Edit the `EXAMPLE_PROMPTS` array. These should reflect the queries staff most commonly use. Review the GA search data periodically to inform this.

### Adjusting relevance scoring

The `scorePages` function controls which pages are sent to Claude. You can adjust:

- **`topN`** (default: 20) — how many pages are sent per request. Increase for more context; decrease to reduce token usage further.
- **Point values** — the weights assigned to title, tag, excerpt, and content matches. Increase title weight if title-based relevance is most important for your site.
- **Fuzzy match threshold** — currently allows 1 character difference for words of 5+ characters. Increase for more aggressive typo tolerance.

### Changing the AI model

The model is set in the `runSearch` function:

```js
model: "claude-sonnet-4-20250514",
```

Anthropic releases new model versions periodically. To upgrade, update the model string. Check the [Anthropic documentation](https://docs.anthropic.com) for the latest available model names. Newer models may return results in a different format — test thoroughly before deploying.

### Modifying the AI behaviour

The `systemPrompt` string in `runSearch` controls how Claude interprets queries. Current behaviours configured there:

- Abbreviation expansion (ABL, AIR, APEX, HEA, etc.)
- Minimum relevance score threshold (35)
- Instruction to return valid JSON only
- Instruction to note content gaps
- When no pages scored, instruction to acknowledge this honestly rather than returning low-confidence results

Edit this string to adjust any of these behaviours.

### Adjusting the crawler

See [Section 4](#4-the-site-crawler-scriptscrawlpy) for details on which constants to change if the Drupal site structure changes.

### Changing the crawl frequency

Edit the cron expression in `.github/workflows/crawl_site.yml`:

```yaml
- cron: '0 2 * * 0'   # Current: weekly, Sunday 2am UTC
```

Use [crontab.guru](https://crontab.guru) to generate alternative expressions.

### Reusing this project for a different site

The scoring logic (`getCorePages`, `scorePages`) contains no CADI-specific assumptions:

- `getCorePages` detects homepage, contact, and about pages by URL pattern — no hardcoded IDs
- `scorePages` works against any `search-index.json` produced by the crawler

To reuse for another UoP department: update `PROXY_URL`, `GITHUB_RAW_INDEX_URL`, `FALLBACK_INDEX`, `EXAMPLE_PROMPTS`, the abbreviation expansion list in `systemPrompt`, and any CADI-specific priority pages or external tool links.

## 12. Troubleshooting

**"Demo mode" message appears instead of search results**

`PROXY_URL` still contains `YOUR-SUBDOMAIN`. Update it to the actual Cloudflare Worker URL and redeploy.

**"Search failed — please try again" error**

The Cloudflare Worker is returning an error. Check:
1. The Worker is deployed and the URL is correct
2. The `ANTHROPIC_API_KEY` secret is set on the Worker
3. The Anthropic API key is valid and has available credits in the [Anthropic Console](https://console.anthropic.com)
4. Open browser DevTools → Network tab → look at the failed request for the raw error message from the API

**Claude returns a message saying it could not find relevant results**

When the local scoring step produces a `maxScore` of 0, Claude is instructed to be transparent about this rather than return unrelated results. This is expected behaviour for queries that are too vague, contain unusual terminology, or refer to content not yet in the index. Suggest the user tries a more specific query or triggers a fresh crawl if the content should exist on the site.

**A relevant page is missing from results**

The page may not have scored highly enough to appear in the top 20 sent to Claude. Check:
1. Open `search-index.json` and confirm the page exists and has a meaningful `title`, `tags`, and `content` field
2. If `content` is thin or contains navigation boilerplate, update `CONTENT_SELECTORS` or `NOISE_TAGS` in `crawl.py` and re-run the crawl
3. Adding relevant terms to the page's `tags` in the index (by improving the crawler's tag extraction) will improve its score for related queries

**Results seem stale or missing recently published pages**

The search index is refreshed weekly. Either wait for the next Sunday crawl, or trigger a manual run via GitHub Actions (see [Section 6](#6-github-actions-automated-crawling)).

**The GitHub Actions crawler fails with "No pages indexed"**

The crawler may be blocked, the site may be temporarily down, or a selector change in the Drupal theme has broken content extraction. Check the Actions run log for error details. Run the crawler locally to debug:

```bash
python scripts/crawl.py --url https://cadi.port.ac.uk --max-pages 10
```

**The index fetches but results are poor quality**

The content being extracted by the crawler may be thin or noisy. Check the `content` field in `search-index.json` for the pages in question. If it contains mostly navigation text rather than page content, update `CONTENT_SELECTORS` or `NOISE_TAGS` in `crawl.py`.

**CORS error when fetching the GitHub index**

GitHub's raw content endpoint (`raw.githubusercontent.com`) returns permissive CORS headers for public repositories. If the repository is private, the browser will not be able to fetch the file directly. Either make the repository public, or host `search-index.json` on a server that sets `Access-Control-Allow-Origin: *`.
